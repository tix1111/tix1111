## 5. RBAC 权限模型

### 5.1 核心对象

| 对象 | 说明 |
| --- | --- |
| 用户 | 系统登录主体 |
| 角色 | 权限集合，如系统管理员、部门管理员、普通用户 |
| 模块 | 业务模块，如项目管理、财务管理 |
| 菜单 | 前端主菜单和二级菜单 |
| 权限点 | API 操作权限，如新增、编辑、删除、导出、审批 |
| 数据范围 | 本人、本部门、多部门、全部、自定义 |

### 5.2 权限层级

1. 模块权限：决定是否可以进入业务模块。
2. 菜单权限：决定主菜单和二级菜单是否展示。
3. 操作权限：决定页面按钮、API 操作是否可用。
4. 数据权限：决定可查询、审批、导出哪些数据。

### 5.3 动态菜单流程

1. 用户登录成功。
2. 服务端查询用户角色。
3. 服务端合并角色绑定的模块、菜单、权限点。
4. 服务端过滤停用菜单、隐藏菜单和无权限菜单。
5. 返回菜单树给前端。
6. 前端按菜单树渲染左侧导航和快捷入口。
7. 用户访问 API 时，后端再次根据会话和权限点校验。

### 5.4 系统管理员可维护内容

1. 模块新增、修改、删除、启停。
2. 菜单新增、修改、删除、排序、图标、路由。
3. 角色新增、修改、删除、授权。
4. 用户新增、修改、禁用、重置密码、分配角色。
5. 数据权限范围配置。
6. 审批流程、表单、字典、参数配置。

### 5.5 权限、岗位和审批身份关系

RBAC 只解决“能不能看、能不能操作”的问题，审批还需要解决“该谁处理”的问题。两者关系如下：

| 概念 | 用途 | 示例 | 说明 |
| --- | --- | --- | --- |
| 用户 | 登录主体 | admin、dpt1、user1 | 一个用户可以拥有多个角色 |
| 角色 | 权限集合 | 系统管理员、部门管理员、普通用户 | 决定菜单、按钮、API 权限 |
| 部门 | 组织归属 | 技术部、财务部、党支部 | 决定默认数据范围和审批组织关系 |
| 岗位 | 业务职责 | 项目经理、财务主管、支部书记 | 可作为审批节点候选人 |
| 数据范围 | 可访问数据边界 | 本人、本部门、全部 | API 查询和导出必须使用 |
| 审批身份 | 流程处理身份 | 发起人直属上级、部门负责人、财务复核 | 由审批流程运行时计算 |

落地规则：

1. 角色不等于岗位。角色控制系统权限，岗位用于组织和审批路由。
2. 部门管理员默认不是所有模块管理员，只是拥有本部门数据范围的授权角色。
3. 审批流程不能只写死用户，应优先支持岗位、部门负责人、项目负责人、合同负责人等动态审批人。
4. 一个用户如果同时拥有多个角色，最终权限取并集，数据范围按最小必要原则取交集或按授权策略明确配置。
5. 涉密数据、附件下载、数据导出应在普通 RBAC 外增加密级校验。

### 5.6 数据权限判定规则

数据权限需要按业务对象统一落地：

| 数据范围 | 判定方式 | 适用场景 |
| --- | --- | --- |
| 本人 | `created_by = 当前用户` 或 `owner_id = 当前用户` | 普通用户查看本人提交单据 |
| 本部门 | `department_id = 当前用户部门` | 部门管理员查看部门业务 |
| 参与项目 | 当前用户在项目成员表中 | 项目成员查看项目文档、任务、工程 |
| 审批相关 | 当前用户是发起人、审批人、抄送人 | 审批中心、待办中心 |
| 多部门 | 用户被授权多个部门 | 分管领导、区域负责人 |
| 全部 | 系统管理员或被显式授权 | 全局管理、审计、备份 |
| 自定义 | 按客户、项目、合同、密级组合授权 | 涉密项目、重点客户、专项工程 |

API 实现时必须先计算用户可访问范围，再拼接业务查询条件；前端只展示结果，不自行判断数据范围。
